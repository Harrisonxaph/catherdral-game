# Phase 2 persistent development / independent-review loop

Status: **proposed coordination system, not gameplay authorisation**. Owner approval is required for the product choices in [SPEC.md §10](SPEC.md#10-approval-and-independent-review-gates) before Phase 2 implementation. The loop can be prepared without that approval. Do not treat this plan, an issue, a PR, an earlier chat message or an instruction to "set up the loop" as approval of gameplay defaults.

## Sources of truth and roles

- **Precedence:** live GitHub state (issues #32–#36, PRs, PR comments, CI runs) and current merged main take precedence over dated prose in these files. Document conflicts; do not guess.
- **Claude Code = developer:** inspects current main, implements one authorised PR, adds tests, runs checks, pushes a focused branch and posts the developer handoff comment.
- **Codex = independent reviewer:** starts from a fresh session, reviews the exact latest pushed PR head against that stage's issue, posts a verdict comment naming the SHA it reviewed. Codex must NOT implement, push or silently fix the PR it is reviewing; its self-review is not independent.
- **Owner = decision maker:** approves product policy, any expanded scope, each stage's start, each PR merge and any deployment. No auto-merge or automatic production changes.
- **GitHub Actions = automated verifier:** existing `.github/workflows/quality.yml` performs unit/docs/build/browser/graphics checks on PRs. Do not label checks green before the completed run is inspected.
- **Prompts:** [PHASE2-PROMPTS.md](PHASE2-PROMPTS.md). One reusable developer prompt and one reviewer prompt serve all five PRs. Users start Claude and Codex sessions manually; files in GitHub alone do not schedule or invoke either agent.

## Where each record lives

A tracked file cannot contain the SHA of the commit that includes its own final update. Records are therefore split by when the evidence exists:

| Record | Location | Written by | When |
|---|---|---|---|
| Stage status, approvals (links), correction-cycle counts, base SHA, PR URL, history | [PHASE2-STATUS.md](PHASE2-STATUS.md) | Claude, inside the stage's own commits | With the work it describes |
| Exact pushed head SHA, checks run, evidence | **Developer handoff** comment on the PR | Claude | After each push, once the commit exists |
| Reviewed head SHA, verdict, findings | **Codex review** comment on the PR | Codex | After reviewing that exact head |
| Merge commit SHA of stage *n* | PHASE2-STATUS.md | Claude | In stage *n+1*'s first commit (the merge commit then already exists on main) |
| Owner approvals and merge decisions | **Owner approval** comment on the issue or PR, linked from PHASE2-STATUS.md | Owner only | When the owner decides |

Rules:
- Never commit solely to record a SHA. PHASE2-STATUS.md records the *base* SHA (an existing commit), the PR URL, statuses and counts; exact heads live in PR comments.
- The correction count in PHASE2-STATUS.md is updated inside the correction commit itself (the count is known before committing). The handoff comment then names that commit's SHA.
- Keep history append-only: add entries, never rewrite or delete earlier ones.
- If the STATUS count and the PR's handoff comments disagree, use the **higher** count and report the discrepancy.

## Approval evidence

Claude and Codex may post GitHub comments under the owner's account, so a comment's author does not by itself prove owner approval. An approval counts only when **all** of these hold:

1. It is a comment on the relevant issue or PR whose first line begins `OWNER APPROVAL:` and names the stage (for example `OWNER APPROVAL: P2 PR1 (#32)`), or a commit by the owner ticking the gate boxes in PHASE2-STATUS.md;
2. it carries no AI attribution footer ("Generated by Claude Code", a Codex receipt or similar);
3. its scope covers the action about to be taken.

Agents must never write text beginning `OWNER APPROVAL:`, tick owner gate boxes, or treat chat messages, issue status, labels, this file or a prior session's summary as approval. These are conventions, not technical enforcement; if anything looks inconsistent, stop with `NEEDS_OWNER_APPROVAL`.

**Current stage** = the earliest issue in this order that is still open and has no owner-merged PR. A stage is **eligible** only when every earlier stage's PR is merged on main *and* an approval record (above) authorises this stage. Each issue's live **Scope** and **Acceptance evidence** are that PR's acceptance criteria; the stage invariants in [PHASE2-PROMPTS.md](PHASE2-PROMPTS.md#stage-invariants) add checks, never replace the issue.

PR1 is infrastructure for later durability, **not permission to tune or rewrite melee, bosses, ability values or enemy AI**. PR3 makes approved combat-resource transitions durable, not a full combat redesign. Combat-balance changes need their own scoped acceptance criteria and owner approval.

## Context strategy

Read in two levels. Saving usage never justifies skipping a correctness, safety or security check.

**Core context (every session):**
- `AGENTS.md` (loaded automatically by Claude via `CLAUDE.md`), this file and PHASE2-STATUS.md on main and, when one exists, on the stage's PR branch;
- the current stage's issue (body and comments) and any open PR for it: metadata, latest head SHA, diff, CI, comments and review threads;
- [SPEC.md §10](SPEC.md#10-approval-and-independent-review-gates) and the approval records, to decide whether work may proceed.

**Targeted context (only when the work touches it):**
- the SPEC sections and the ROADMAP Phase 2 text relevant to the stage; [AUDIT.md](AUDIT.md) rows for the files being changed;
- source and tests of modules the diff touches, their direct callers and the tests that cover them;
- `PROJECT.md`, `DECISIONS.md` and `TASKS.md` sections about ARPG and the current stage; older history (`docs/history/`, graphics reports, earlier PR threads) only when a specific question needs it.

For Phase 2 loop sessions this two-level reading satisfies AGENTS.md's start-here reading list; read further whenever a finding, failure or unclear requirement calls for it.

## Bounded loop — each PR

1. **SELECT AND GATE:** Determine the current stage (above). If an open PR already exists for it, resume that PR instead of starting another. Confirm every earlier stage is merged on main and an approval record covers this stage. Missing or ambiguous: **STOP: NEEDS_OWNER_APPROVAL**. Read-only analysis, test design or a documentation-only proposal is then allowed; no gameplay implementation.
2. **PLAN:** Take the acceptance criteria from the live issue. Identify the smallest implementation consistent with the issue, SPEC, current code and existing test contracts. Write measurable checks, failure-injection cases, scope exclusions and rollback risks. Respect simulation time, the existing item `mods` schema, once-only rewards, mobile controls, Canvas fallback and graphics v2.
3. **IMPLEMENT:** Use only a dedicated development branch from current main; preserve main and other PRs. Add tests that fail on regression, ideally showing a before/after result. Keep changes narrow: no framework migration, hidden QA globals, unlicensed assets or paid compute.
4. **VERIFY:** Run `npm test`, `npm run build`, `python3 .github/scripts/check_agent_docs.py`, relevant unit/browser/offline suites and `npm run test:graphics-budget` (or the PR CI graphics-budget job) where appropriate. Record commands, pass/fail/skipped counts and environmental limits. Browser suites need Playwright and Chromium provisioned outside application dependencies. Physical devices are *not verified* unless actually tested. Never modify baselines to make failures pass.
5. **PUBLISH:** Commit the work together with its PHASE2-STATUS.md entry (status, base SHA, correction count), push, open a **draft PR** linking the issue, then post the **developer handoff** comment with the exact pushed head SHA and evidence. Stop with `AWAITING_INDEPENDENT_REVIEW`.
6. **REVIEW:** A fresh Codex session reviews the latest pushed head against the issue's criteria, observes CI, and posts a **review** comment naming that SHA. No findings means "no findings on this head", not guaranteed correctness or merge approval.
7. **ADAPTIVE CORRECTION:** For blocking findings Claude fixes the root cause with a regression test, re-verifies, commits the fix with the incremented count in PHASE2-STATUS.md, pushes, and posts a new handoff comment. Codex re-reviews **that new head**. Each reviewer-driven fix submission is **one correction cycle**; at most **3 per PR after its initial implementation**. Never reset the count by starting a new chat, renaming a branch or changing reviewer. Stop sooner on critical risk, repeated failure without progress, missing permissions or policy ambiguity. Do not weaken tests or hide failures.
8. **STOP / HANDOFF:** Mark `READY_FOR_OWNER_REVIEW` only when the issue's acceptance criteria, observed required CI and a review of the current head show no unresolved blocking findings. Otherwise `BLOCKED` or `NEEDS_OWNER_APPROVAL`, with findings and evidence. Never self-merge, auto-start the next PR or deploy. After the owner merges, the next stage's first commit records the merge commit in PHASE2-STATUS.md.

**Avoiding duplicate reviews:** Codex reviews a head once. A new review is needed only when the head SHA changes. If the only change since the last verdict is to PHASE2-STATUS.md or the PR description, a short confirmation comment citing the earlier verdict suffices; any code or test change needs a full review of the changed files and their dependencies.

### Required stop states

- `NEEDS_OWNER_APPROVAL`: §10 decisions, a changed requirement or feature, or this stage's authorisation is not recorded as an approval record.
- `BLOCKED`: critical correctness/save-safety problem, unresolved blocking finding after 3 cycles, inaccessible tool/CI, or baseline drift.
- `AWAITING_INDEPENDENT_REVIEW`: a head is pushed with its handoff comment and has no review yet.
- `READY_FOR_OWNER_REVIEW`: test evidence exists, required CI observed, review of the current head complete, no blockers. The owner decides merge.
- `MERGED_BY_OWNER`: merge commit confirmed on main; only now may the next stage receive owner authorisation.

## Non-negotiable acceptance / safety

- Never silently overwrite or degrade character data; preserve backups, item ownership, numeric IDs, durable rewards, schema validation and revision/lease fencing.
- No duplicate XP/ash/potions/loot, no double rewards on replay, no cooldown reset or resource refill exploit introduced by persistence.
- PR1 preserves **the existing seeded draw order and graphics baseline world digests**; stable IDs must not consume additional gameplay random values. Check all five floors and at least the existing 100-seed connectivity coverage.
- No automatic merge, force-push over others, production deployment, branch deletion, purchases, credentials/secrets in source or elevated CI permissions.
- No outside-run claims: if tests cannot run, record the limitation. Simulation/emulator tests are not physical iPhone/Android validation.
- No change to approved combat mechanics, graphics assets, external libraries or unrelated systems unless explicitly authorised.
- Preserve historical source/PRs. New code must pass current `npm run build` and `APP_ASSETS`/service-worker rules when integrated.
- Follow the project's existing handover format ([AGENT-WORKFLOW.md](../AGENT-WORKFLOW.md)). In any conflict, stop and escalate rather than guessing.

## What is automated vs manual

**Already configured:** GitHub PR CI runs tests/build/browser/graphics checks using the existing workflow when its triggers and repository Actions settings allow it. Codex also starts an automatic review when a PR is opened or marked ready; a manual `@codex review` comment re-requests one.

**Persistently configured by this setup (after merge):** shared state, role-specific prompts, per-PR issue tracking, owner gates and the correction budget.

**NOT configured:** unattended Claude-to-Codex invocation, an agent scheduler that reads a finished PR and launches the other assistant, approval/merging, or guaranteed overnight work. Those need separately authorised integrations, credentials, security checks and budget controls. Do not describe this as fully autonomous.
